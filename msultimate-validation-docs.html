[ValidateActiveState]

Validates that a referenced GameObject or Component matches an expected active or inactive state in the scene.

1. Overview & Value Proposition

What it does: [ValidateActiveState] inspects referenced scene GameObject or Component fields. It verifies whether the target object is actively enabled or disabled in the scene at editor evaluation time. It can evaluate either the local active state (activeSelf, default) or the global ancestor chain (activeInHierarchy, via CheckHierarchy = true). If the state fails validation, a customizable validation banner is rendered directly in the Inspector.

The Problem: Complex scenes often contain managers, spawners, or triggers that must start inactive (waiting for scripted activation) or must start active (such as audio listeners or camera rigs). Developers frequently commit scenes where critical managers were accidentally disabled during isolated testing, or where hidden template objects were left active, creating silent initialization bugs and broken level transitions.

The Solution: Decorating fields with [ValidateActiveState]:

  • Active / Inactive Verification: Enforce that target references must be active (mustBeActive = true) or explicitly inactive (mustBeActive = false).
  • Hierarchy-Aware Evaluation: Toggle CheckHierarchy = true to verify that no parent or ancestor in the transform branch has deactivated the object.
  • Customizable Warning Messages: Provide clear, domain-specific alerts ("Boss spawner must start inactive!") with configurable warning/error severity (MessageType).
  • Visual Styling Tokens: Style error badges with custom colors (ErrorColor, ErrorBackgroundColor), fonts, and margins.

2. Quick Start

csharp
using UnityEngine;
using MaharajaStudio.MSUltimate.ValidationModule;

public class MissionManager : MonoBehaviour
{
    [ValidateActiveState(true, "Main Camera must be active in the scene.")]
    public Camera sceneCamera;

    [ValidateActiveState(false, "Cinematic trigger volume must start inactive.")]
    public GameObject endSequenceTrigger;
}

[ValidateAnimatorParameter]

Validates that an assigned Animator contains a specific parameter name and matching parameter type.

1. Overview & Value Proposition

What it does: [ValidateAnimatorParameter] inspects an assigned Animator or RuntimeAnimatorController field. It interrogates the controller's parameter definitions to verify that a required parameter exists (ParameterName) and matches the expected type (AnimatorControllerParameterType: Float, Int, Bool, or Trigger). If the parameter is missing or has an incompatible type, a high-visibility error banner is displayed.

The Problem: In Unity gameplay scripting, animators are controlled using string-based or hash-based API calls (animator.SetFloat("Speed", 5f), animator.SetTrigger("Jump")). If an animator designer renames "Speed" to "MoveSpeed", or changes a parameter from Float to Bool, Unity provides zero compile-time or inspector warnings. The script continues running silently without driving animations, leaving programmers to debug animator state machines by hand.

The Solution: Decorating fields with [ValidateAnimatorParameter]:

  • Instant Parameter Verification: Verifies parameter presence immediately in the Inspector upon assigning an Animator or Controller.
  • Type Safety Enforcement: Guarantees that the expected parameter type (Float, Int, Bool, Trigger) matches script expectations.
  • Clear Diagnostic Messages: Displays clear error banners indicating the exact missing parameter and expected data type.
  • Descriptive Studio Feedback: Prevents broken character rigs from reaching QA or production builds.

2. Quick Start

csharp
using UnityEngine;
using MaharajaStudio.MSUltimate.ValidationModule;

{

[ValidateAssetExtension]

Validates that a referenced project asset matches a required file extension (e.g. .png, .fbx, .json, .wav).

1. Overview & Value Proposition

What it does: [ValidateAssetExtension] inspects assigned project asset references (UnityEngine.Object, DefaultAsset, TextAsset, AudioClip, etc.) and string file paths. It interrogates the asset's project database path (AssetDatabase.GetAssetPath) and validates that its file extension matches the expected extension format (ExpectedExtension). If the assigned file has an incorrect extension (such as assigning a .mp3 where .wav is required, or assigning .txt instead of .json), it displays a clear validation error.

The Problem: Generic Unity asset slots like DefaultAsset, TextAsset, or Object accept any file type from the Project window. In data-driven pipelines, developers expecting .json config files can accidentally drag in .xml or .csv files. Similarly, audio pipelines requiring uncompressed .wav assets can receive compressed .mp3 files, causing runtime parse failures or unexpected compression artifacts.

The Solution: Decorating asset fields with [ValidateAssetExtension]:

  • Format Enforcement: Guarantees that only assets matching the designated extension (e.g. ".json", ".fbx", ".png") can be assigned.
  • Automatic Extension Normalization: Accepts extensions with or without leading periods ("json" or ".json"), formatting them consistently.
  • Early Pipeline Guard: Catches wrong asset types at the moment of assignment rather than during runtime asset loading or build execution.
  • Custom Error Messages: Supply clear studio instructions to guide artists and designers to the correct source assets.

2. Quick Start

csharp
using UnityEngine;
using MaharajaStudio.MSUltimate.ValidationModule;

public class LocalizationDataLoader : MonoBehaviour
{
    [ValidateAssetExtension(".json", "Localization database must be a .json file.")]
    public TextAsset localizationFile;

[ValidateAssetPath]

Validates that a string path refers to an existing asset in the Unity project, with optional asset type assignment verification.

1. Overview & Value Proposition

What it does: [ValidateAssetPath] validates string fields representing project-relative paths (e.g. "Assets/Configs/WeaponData.asset" or Resources / Addressable path keys). It verifies that an asset physically exists at the specified project path via AssetDatabase.LoadAssetAtPath, and optionally confirms that the asset is assignable to an expected type (ExpectedType).

The Problem: String-based asset loading (such as Resources.Load, AssetDatabase.LoadAssetAtPath, or custom procedural asset loaders) is vulnerable to typos, broken file renames, and moved folders. Because strings cannot be verified at compile time, broken paths go unnoticed until runtime loading fails, throwing null references during critical gameplay or initialization sequences.

The Solution: Decorating string path fields with [ValidateAssetPath]:

  • Real-Time Path Existence Verification: Confirms that the target asset actually exists in the project asset database.
  • Type Compatibility Enforcement: When ExpectedType is provided (e.g. ExpectedType = typeof(ScriptableObject)), verifies that the loaded asset matches the required type.
  • Immediate Visual Error: Displays an inspector error banner as soon as a path string is mistyped or points to a non-existent location.
  • Configurable Severity: Toggle between Error and Warning states to suit development vs. production build stages.

2. Quick Start

csharp

[ValidateChildCount]

Validates that a referenced GameObject's direct child count falls within specified minimum and maximum bounds.

1. Overview & Value Proposition

What it does: [ValidateChildCount] inspects referenced GameObject or Component fields. It counts the target object's direct child transforms (transform.childCount) and asserts that the count satisfies required minimum (MinChildren) and maximum (MaxChildren) bounds. It supports including or excluding inactive child GameObjects via IncludeInactive.

The Problem: In modular game architecture, many gameplay entities rely on strict child hierarchy structures. For instance, a 4-player spawn container must have exactly 4 spawn nodes; a weapon socket must have at least 1 muzzle transform; or an inventory UI row must not exceed 8 slot items. When level designers accidentally add too few or too many child nodes, systems break silently or crash with IndexOutOfRangeException at runtime.

The Solution: Decorating reference fields with [ValidateChildCount]:

  • Hierarchy Boundary Enforcement: Enforces strict min/max limits on child transform counts directly in the Inspector.
  • Support for Inactive Children: Toggle IncludeInactive = false to evaluate only actively enabled child GameObjects.
  • Informative Error Messages: Displays an immediate, formatted alert banner whenever the child count falls outside valid parameters.
  • Prevents Structural Defects: Protects procedural spawner rigs, vehicle wheel hierarchies, and UI container layouts from structural corruption.

Validation Module/Validation Attributes/[ValidateUnless]

[ValidateUnless]

Conditionally bypasses sibling validation attributes on the same field whenever a specified predicate condition evaluates to true.

1. Overview & Value Proposition

What it does: [ValidateUnless] is the inverse counterpart of [ValidateIf]. It functions as an execution bypass gate for sibling validation attributes declared on the same field (such as [ValidateNotNull], [ValidateRange], or [ValidateComponent]). It monitors a condition member (ConditionMember: a boolean field, enum value, or property). When that condition evaluates to true (or matches ExpectedValue), the sibling validation attributes on the field are skipped. Conversely, when the condition is false (or does not match), the validation rules are actively enforced.

The Problem: Game configurations frequently utilize default fallback modes, debug bypass toggles, or automated procedural overrides:

  • An audio clip or material reference is required unless useGlobalDefaults is toggled on.
  • A network matchmaking token is mandatory unless offlineMode == true.
  • An AI behavior tree asset must be assigned unless useProceduralDirector == true.

Without [ValidateUnless], developers must write inverted boolean flags (isNotOfflineMode, doNotUseGlobalDefaults) or invent convoluted condition wrappers just to avoid false positive validation alerts on optional fields.

The Solution: Decorating fields with [ValidateUnless]:

  • Intuitive Negative Conditionals: Eliminates confusing double-negative boolean flags by expressing "validate unless X is true".
  • Conditional Bypass Gates: Skips validation when global defaults, mock systems, or procedural alternatives are active.
  • Enum and Primitive Matching: Supports exact value comparisons (expectedValue = GameMode.Creative).
  • Clean Inspector Experience: Keeps the Inspector free of false positive alerts when features are intentionally bypassed.
