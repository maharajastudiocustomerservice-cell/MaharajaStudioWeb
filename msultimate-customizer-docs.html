Inspector Customizer/Overview

MSUltimate - Inspector Customizer Documentation

Visual UI Toolkit Templating, Non-Destructive Inspector Styling, Makeover Node Graphs, and AI-Powered Layout Suite.
Official Addon for Maharaja Studio Ultimate Inspector Suite (MSUltimate). Compatible with Unity 6 (6000.x)+.

1. System Overview

MSUltimate Inspector Customizer is a dual-pipeline visual styling and layout engine designed to transform flat, unstyled Unity Inspectors into production-grade UI Toolkit workspaces—without requiring changes to underlying C# scripts.

Traditional Unity inspector customization requires developers to manually decorate fields with dozens of attributes in code or author complex custom Editor scripts. Inspector Customizer decouples visual presentation from game logic:

  1. Virtual Runtime Hydration Layer: Visually apply, reorder, group, and tune MSUltimate attributes inside a visual editor window. Overrides are serialized into lightweight ScriptableObject profiles (InspectorProfile) and dynamically injected into Unity's inspector pipeline at draw-time via ModularMonoBehaviourEditor.
  2. Deterministic Source Code Baker: When you are ready to commit your inspector layout directly to your codebase, 1-Click Code Baking safely injects attributes into your C# script source with syntax-highlighted diff review and namespace resolution.
  3. Makeover Graph Pipeline: A 30-node visual logic canvas built on UI Toolkit GraphView. Define pattern-matching rules, companion field pairings (e.g. min*/max* sliders), dynamic progress bar bindings, and layout wrappers.
  4. Multi-LLM AI Decorator: Intelligent inspector generation powered by OpenAI, Claude, Gemini, Ollama, Groq, Mistral, and custom endpoints. Features Studio Privacy Shield (local key encryption and code scrubbing) to protect proprietary game logic.

Inspector Customizer/01 · Getting Started/Override Modes & Precedence Resolution

Override Modes & Precedence Resolution

Module: MSUltimate Inspector Customizer — Getting Started
Topic: The Three Override Modes, Conflict Handling, and Inheritance Rules

1. Overview of the Three Modes

Every component entry inside an InspectorProfile can operate in one of three distinct modes defined by InspectorOverrideMode:

csharp
namespace MaharajaStudio.MSUltimate.InspectorCustomizer
{
    public enum InspectorOverrideMode
    {
        EditorOverride,
        CodeOnly,
        Both
    }
}

You can toggle the mode at any time using the mode dropdown in the top toolbar of InspectorCustomizerWindow or BakeCodePreviewWindow.

2. Detailed Behavior of Each Mode

ModeSource Code AttributesProfile Virtual OverridesConflict WinnerBest Used For
Both (Default) Active ActiveProfile WinsProduction teams where developers author basic attributes in code, and designers polish visual styles and grouping in Customizer.
EditorOverride Ignored ActiveProfile OnlyTotal inspector redesigns where legacy or third-party code attributes must be completely suppressed without altering packages.
CodeOnly Active BypassedCode OnlyDebugging or testing the pure raw C# inspector without deleting your profile data.

3. Precedence & Conflict Resolution Rules

When running in Both mode, multiple sources can declare attributes on the same member. MSUltimate resolves conflicts using a deterministic 4-tier precedence hierarchy:

TEXT
[Highest Priority]
       ▲
       │  1. Profile Override (Specific Member & Value)
       │  2. Profile Grouping Override (Wrap in BoxGroup / Foldout)
       │  3. Code-Declared Modular Attribute ([ProgressBar], [Range])
       │  4. Unity Built-in Decorator ([Header], [Space], [Tooltip])
       │
[Lowest Priority]

Conflict Scenarios

Scenario 1: Same Attribute Type on the Same Field

  • Code declares: [Range(0f, 10f)] public float speed;
  • Profile declares: Range(0f, 100f)
  • Resolution: The profile value takes precedence (0f to 100f). The code attribute is suppressed.

Scenario 2: Complementary Attributes on the Same Field

  • Code declares: [ReadOnly] public int score;
  • Profile declares: [ProgressBar(0, 1000, "#00FF00")]
  • Resolution: Both attributes stack! The member is drawn as a read-only progress bar.

Scenario 3: Class-Level Header Conflicts

  • Code declares: [ComponentHeader("Old Title")]
  • Profile declares: [ComponentHeader("Enhanced HUD", "#FF5500")]
  • Resolution: The profile [ComponentHeader] replaces the code header entirely.

4. Switching Modes Dynamically

You can switch modes without data loss:

  • Switching from Both to CodeOnly temporarily deactivates profile styling in the Inspector while preserving all your configured cards in the profile asset.
  • Switching to EditorOverride allows you to test clean-room visual redesigns of complex legacy components.
Inspector Customizer/01 · Getting Started/System Architecture & Technical Foundation

System Architecture & Technical Foundation

Module: MSUltimate Inspector Customizer — Getting Started
Topic: Dual-Pipeline Architecture, Virtual Attribute Hydration, and Execution Lifecycle

1. Dual-Pipeline Design Philosophy

Traditionally in Unity, styling an inspector requires either writing attributes directly into gameplay scripts ([BoxGroup], [ProgressBar], [ShowIf]) or authoring custom Editor scripts extending Editor. While attributes improve ergonomics, they intertwine visual inspector styling with gameplay code. If a designer wants to change a progress bar color, reorganize groups, or hide debug properties, they must edit source code, trigger script compilation, and risk merge conflicts in Git.

MSUltimate Inspector Customizer introduces a dual-pipeline decoupled architecture:

TEXT
[Developer / Designer Choice]
         │
         ├───► Pipeline A: Virtual Hydration (Default)
         │     • Zero code modification
         │     • Zero domain reloads / script recompilation
         │     • Overrides stored in lightweight ScriptableObject profiles
         │     • Dynamically injected at draw-time via InspectorCustomizerBridge
         │
         └───► Pipeline B: Source Code Baking (On-Demand)
               • Converts virtual overrides into permanent C# attributes
               • Safe AST parsing and injection via AttributeCodeBaker
               • Full diff preview and syntax highlighting
               • Zero external runtime dependencies when exported

2. Core Data Structures

All customization data is represented through three lightweight serializable classes defined in MaharajaStudio.MSUltimate.InspectorCustomizer:

2.1 SerializedKVP

Stores attribute constructor arguments and named properties as string pairs.

csharp
[Serializable]
public class SerializedKVP
{
    public string Key;   // e.g. "__ctor_min_Single", "SliderColor", "Height"
    public string Value; // e.g. "0.0", "#FF4444", "24"
}
  • Constructor Arguments: Stored with key format __ctor_<paramName>_<typeName> (e.g. __ctor_min_Single, __ctor_lines_Int32).
  • Named Properties: Stored directly using the property name (SliderColor, ShowPercentage, Height).
  • Hydration Conversion: Strings are parsed into strongly typed objects (string, bool, int, float, double, long, Enum by name or flag integer, Color/Color32 with or without #, Vector2 as "x,y", Vector3 as "x,y,z", and 1D arrays of any primitive type delimited by ,, ;, |, >, ›, or /) at draw-time by AttributeHydrator.

2.2 FieldAttributeOverride

Represents an applied virtual attribute on a target member:

csharp
[Serializable]
public class FieldAttributeOverride
{
    public string MemberName;             // Name of target field or method
    public bool IsMethod;                 // True for methods, false for fields
    public bool IsClassLevel;             // True for class/component-level attributes
    public string AttributeTypeName;       // Assembly-qualified type name
    public bool IsDisabled;               // Temporarily muted in inspector
    public bool IsCollapsed;              // Collapsed in the Customizer editor deck
    public List<SerializedKVP> Values;    // Serialized parameters
}

2.3 TypeProfileEntry & InspectorProfile

Container ScriptableObject storing overrides organized by component type:

csharp
[CreateAssetMenu(menuName = "Maharaja Studio/MSUltimate/Inspector Customizer/Inspector Profile")]
public class InspectorProfile : ScriptableObject
{
    public List<TypeProfileEntry> TypeEntries = new List<TypeProfileEntry>();
}

3. Draw-Time Hydration Lifecycle

When a component is selected in the Unity Inspector, MSUltimate's core drawer engine executes the following pipeline:

mermaid
sequenceDiagram
    autonumber
    actor Dev as Developer / Unity Editor
    participant Editor as ModularMonoBehaviourEditor
    participant Bridge as InspectorCustomizerBridge
    participant Registry as InspectorProfileRegistry
    participant Hydrator as AttributeHydrator
    participant Drawer as DrawerDatabase

    Dev->>Editor: Inspect GameObject / Component
    Editor->>Bridge: Query Active Override Mode for TargetType
    Bridge->>Registry: Lookup InspectorProfile for TargetType
    Registry-->>Bridge: Return TypeProfileEntry & Mode (Both / Override / CodeOnly)
    
    loop For each Member (Field, Property, Method, Class)
        Editor->>Bridge: GetVirtualAttributes(TargetType, MemberName)
        Bridge->>Hydrator: Hydrate FieldAttributeOverride list into ModularAttribute instances
        Hydrator-->>Bridge: Return instantiated & configured attribute objects
        Bridge-->>Editor: Merge with code attributes according to Mode rules
        Editor->>Drawer: Resolve drawer and render UI Toolkit VisualElement tree
    end
    
    Editor-->>Dev: Display fully styled, interactive UI Toolkit Inspector
  1. Bridge Interception: ModularMonoBehaviourEditor checks InspectorCustomizerBridge.IsCustomizerAvailable.
  2. Profile Lookup: InspectorProfileRegistry retrieves the active profile for the component type from memory cache (zero disk reads per frame).
  3. Attribute Hydration: AttributeHydrator uses reflection caches to instantiate the attribute class and assign its constructor parameters and property values.
  4. Drawing & Stacking: Core drawers (DrawerDatabase) receive the instantiated attributes exactly as if they were written in C# source code, rendering headers, progress bars, foldouts, and interactive controls seamlessly.

4. Performance & Memory Profile

  • Zero Runtime Overhead: All Inspector Customizer classes are editor-only or reside in lightweight editor-bound assemblies. In standalone game builds (Windows, Mac, iOS, Android, Consoles), no customizer code or reflection overhead executes.
  • Aggressive Reflection Caching: Member queries, attribute constructors, and parameter parsers are cached in static dictionaries upon first access. Inspector repaints operate at native UI Toolkit speed (under 0.2ms per draw call).
  • Non-Allocating Hydration: Attribute instances created during hydration are pooled and cached until the profile is modified or target selection changes.

  1. In your Unity Scene, select any GameObject with a MonoBehaviour (for example, a character controller or combat script).
  2. Right-click the component's header bar in the Inspector window.
  3. Select MSUltimate > ⚡ Magic Makeover (1-Click Auto-Detect).

3. Option B: Visual Step-by-Step Customization

Follow this walkthrough to visually customize fields and methods manually:

Step 1: Open the Inspector Customizer Window

Go to the Unity top menu bar: Tools > Maharaja Studio > MSUltimate > Inspector Customizer > Inspector Customizer (Or press Ctrl+Alt+I if configured).

Step 2: Select Your Target Component

  • Drag any GameObject, Component, or ScriptableObject into the Target Object field at the top left.
  • Alternatively: Click the Type Picker icon to browse and pick any C# class or POCO data struct across your project.

Step 3: Select a Member to Customize

In the left column:

  • Click Component to add class-level card styling ([ComponentHeader], [ComponentBorder]).
  • Click Fields to view serialized variables. Click on any field (e.g. currentHealth or moveSpeed).

Step 4: Add an Attribute

  1. In the right column, click the green + Add Attribute button.
  2. The Attribute Picker window opens. Type ProgressBar into the search field.
  3. Click ProgressBar. A new attribute card appears in your deck.

Step 5: Adjust Parameter Values Live

  • Notice the parameter fields inside the card: Min, Max, Color.
  • Change Max to 100 and pick a vibrant color using the color picker.
  • Look at your Unity Inspector window: The field instantly renders as a live progress bar! No script compilation required.

Step 6: Save Your Profile

  • Inspector Customizer automatically creates and saves an InspectorProfile asset into Assets/InspectorProfiles/{TargetTypeName}.asset (or your project's configured profile repository under {MSUltimateRoot}/Profiles/).
  • All team members who pull your project will see the styled inspector automatically.

4. Reverting or Clearing Overrides

To remove customizer overrides and restore the default inspector:

  • Right-click the component header → MSUltimate > 🗑️ Clear Customizer Overrides.
  • Or inside InspectorCustomizerWindow, select the member and click the trash can icon on the attribute card.

Right-clicking any card header or clicking the [⋮] button opens a context menu with 10 powerful utilities:

  2. 📄 Copy C# Code: Formats this single attribute into runnable C# code (e.g. [ProgressBar(0f, 100f, SliderColor = "#33CC66", Height = 22)]) and copies it to the system clipboard.
  3. 📋 Paste Parameter Values: Pastes copied parameter values from another attribute of the same type without altering other attributes on the member (disabled if clipboard is empty).
  4. 🔄 Reset to Default Values: Reflects the default constructor and property parameters of the attribute type and overwrites all values with factory defaults.
  5. 🌐 Apply to All Other Fields: Clones this exact attribute configuration onto every other field on the target component in a single click (available on field-level attributes).
  6. 👥 Apply to All {N} Selected Members: When multi-member selection is active (Ctrl+Click / Shift+Click), clones or updates this attribute across all currently selected members simultaneously.
  7. 🔇 Mute Attribute / 🔊 Unmute Attribute: Toggles IsDisabled = true/false on this single attribute, temporarily bypassing it during drawing without removing configured values.
  8. ⧉ Duplicate: Creates an exact clone of the attribute card in the stack (supported on attributes allowing multiple instances).
  9. 💾 Save Attribute as Recipe...: Saves this configured attribute and its parameters directly into your project's recipe library as a new InspectorAttributeRecipe ScriptableObject.
  10. ✕ Remove Attribute: Deletes the override from the profile with full Undo tracking.

(Note: Vertical execution order in the stack is adjusted directly using the card drag handle ☰ or the nudge buttons [^] and [v] in the card header).

3.1 Constructor Arguments vs. Named Properties

In C#, attributes accept two kinds of inputs:

  1. Positional Constructor Arguments: Passed into the constructor (e.g. new ProgressBarAttribute(0f, 100f)).
    • In Inspector Customizer, these keys are encoded with the prefix __ctor_<paramName>_<TypeName> (e.g. __ctor_min_Single, __ctor_max_Single).
    • Changing constructor values automatically validates against the attribute's constructor signature.
  2. Named Optional Properties: Assigned via object initializer syntax (e.g. SliderColor = "#FF0000", Height = 24).
    • In Inspector Customizer, these keys match the exact C# property name.
    • When a named property matches its default value, it is drawn in subtle text; modified properties highlight with an active tint.

3.2 Dynamic Condition Autocomplete

When editing conditional attributes ([ShowIf], [HideIf], [EnableIf], [DisableIf], [ButtonConditional]):

  • Instead of forcing you to remember and type the exact casing of boolean fields, clicking the condition text field opens a live autocomplete popup.
  • The popup lists all bool and enum fields present on the inspected component.
  • Selecting a field inserts its exact identifier into the parameter field, eliminating runtime reflection typos.

2. Category 1: Core & Terminals

2.1 SimpleRule

  • Enum Type: MakeoverNodeType.SimpleRule
  • Purpose: A compound 1-click rule node encapsulating scope, type matcher, name pattern, and attribute action into a single compact node. Eliminates the need to wire multiple condition gates for standard matching.
  • Ports:
    • Scope In (Input, Capacity: Single, Type: object): Optional incoming member signal.
    • Execute Out (Output, Capacity: Multi, Type: Rule): Connects to Output or downstream layout nodes.
  • Exposed Parameters:
    • Target Scope: Any, Field, Method, Class.
    • Type Filter: Any, ExactType, Numeric, Text, Boolean, Color, Enum, SubclassOf, ArrayOrList, UnityObject.
    • Name Match: Contains, StartsWith, EndsWith, Wildcard (e.g. *health), Regex.
    • Action: Attribute to apply and parameter fields.
  • Example Scenario: Match all fields ending in Speed of type Numeric, and apply [Range(0f, 20f)].

2.2 Output

  • Enum Type: MakeoverNodeType.Output
  • Purpose: The mandatory terminal collector of every Makeover Graph. Aggregates all upstream layout rules, resolves conflict priorities, and emits the final layout plan to InspectorProfile.
  • Ports:
    • Rules In (Input, Capacity: Multi, Type: Rule): Multi-wire terminal port receiving rules from all emitters.
  • Exposed Parameters:
    • Conflict Strategy: Skip (keep existing), Replace (override existing), Duplicate (add multiple instances).
  • Wiring Rule: Every valid Makeover Graph must contain exactly one Output terminal.

2.3 MacroInput

  • Enum Type: MakeoverNodeType.MacroInput
  • Purpose: Declares an incoming input boundary pin inside a reusable Subgraph Macro (.msmakomacro).
  • Ports:
    • Pin Out (Output, Capacity: Multi, Type: User-Defined): Routes the incoming data to internal macro nodes.
  • Exposed Parameters:
    • Pin Name: The display label of the input port when viewed from the parent graph.
    • Pin Type: Member, Float, Int, String, Boolean, Color, Generic.

2.4 MacroOutput

  • Enum Type: MakeoverNodeType.MacroOutput
  • Purpose: Declares an outgoing result boundary pin inside a Subgraph Macro (.msmakomacro).
  • Ports:
    • Pin In (Input, Capacity: Single, Type: User-Defined): Receives calculated rule data from internal macro nodes.
  • Exposed Parameters:
    • Pin Name: The display label of the output port on the Macro node in parent graphs.

Relational Sibling Queries & Dynamic Companion Pairing

Module: MSUltimate Inspector Customizer — Makeover Graph
Topic: Companion Field Detection, Relational Sliders, and Dynamic String Extraction

1. The Challenge of Relational Fields

In traditional game development, related variables are often declared as independent adjacent fields:

csharp
public float minDamage = 10f;
public float maxDamage = 50f;

public float currentHealth = 80f;
public float maxHealth = 100f;

public bool enableShield = true;
public float shieldCapacity = 250f;

Standard Unity renders these as flat, disconnected text input boxes. Manually wiring [MinMaxSlider], [ProgressBar], and [ShowIf] requires repetitive attribute coding.

The Makeover Graph solves this automatically using Relational Sibling Queries.

2. Using QuerySiblingField

The QuerySiblingField node inspects the member's parent class to locate companion fields based on naming conventions and stem matching:

mermaid
flowchart LR
    A["Target Member: 'minDamage'"] --> B["QuerySiblingField<br/>Pattern: 'min* -> max*'"]
    B -->|Found: 'maxDamage'| C["AttributeEmitter<br/>[MinMaxSlider(0, 100)]"]
    C --> D["GroupWrapper<br/>HorizontalGroup('Damage Range')"]
    D --> E["Output Terminal"]

Supported Stem Matching Modes

  1. MinMax Pair: Matches min* with max* (e.g. minSpeed → maxSpeed).
  2. StartEnd Pair: Matches start* with end* (e.g. startTime → endTime).
  3. Dimension Pair: Matches width/height or innerRadius/outerRadius.
  4. CurrentMax Pair: Matches current* with max* (e.g. currentMana → maxMana).

3. Dynamic Progress Bar Ceiling Binding

When styling a stat bar like currentHealth, hardcoding Max = 100 breaks when player stats scale up at runtime.

Using QuerySiblingField paired with AttributeEmitter:

  1. ConditionName matches *health*.
  2. QuerySiblingField searches for maxHealth on the same component.
  3. If found, the node dynamically injects the companion field name into the ProgressBarAttribute.MaxMember parameter!
  4. Result: In the Inspector, the progress bar's maximum value dynamically tracks whatever value is currently in maxHealth!

4. Name Parsing with RegexExtractor

The RegexExtractor node enables automatic categorization and labeling by dissecting variable name anatomy:

Example: Auto-Generating Tabs from Prefixes

Given a class with fields:

  • Combat_AttackPower
  • Combat_CritChance
  • Movement_WalkSpeed
  • Movement_SprintMultiplier

Configure RegexExtractor:

  • Pattern: ^(?<category>[^_]+)_(?<label>.+)$
  • Capture Groups:
    • category: "Combat", "Movement"
    • label: "AttackPower", "WalkSpeed"
  • Wire category into GroupWrapper (BeginTabGroup).
  • Wire label into AttributeEmitter[LabelStyle].
  • Result: The graph automatically organizes 40+ raw variables into organized, clean Tab Groups named after their prefixes, stripping messy underscores from variable names!

1. How AST Schema Extraction Works

Large Language Models perform poorly when fed raw, unformatted C# source files filled with thousands of lines of math formulas, update loops, and private algorithms.

To maximize accuracy and minimize token costs, AISchemaExtractor transforms the target component into a compact, token-efficient JSON schema representation:

JSON
{
  "targetClass": "HeroController",
  "namespace": "Game.Characters",
  "baseType": "MonoBehaviour",
  "members": [
    {
      "name": "currentHealth",
      "type": "float",
      "scope": "field",
      "defaultValue": "100.0",
      "siblingCompanion": "maxHealth",
      "docSummary": "Current player hit points"
    },
    {
      "name": "RespawnPlayer",
      "type": "void",
      "scope": "method",
      "parameterCount": 0,
      "docSummary": "Resets health and moves player to spawn point"
    }
  ]
}

Benefits of Schema Extraction

  • 90% Token Reduction: A 1,500-line C# file that would cost 6,000 tokens is condensed into a 250-token schema.
  • Privacy Enforcement: Internal gameplay formulas are never parsed or sent.
  • Accurate Model Attention: The model focuses purely on variables, data types, and companion relationships.

2. Layout Compilation (AILayoutCompiler)

Once the AI generates its response, AILayoutCompiler parses and verifies the JSON output:

      "memberName": "currentHealth",

  1. Type Safety Check: Verifies that every recommended attribute actually exists in the MSUltimate assembly.

Intelligent Makeover Passes

Module: MSUltimate Inspector Customizer — Templates & Recipes
Topic: Automated Heuristic Passes: Relational Pairing, Dynamic Binding, Toggle Cascades, and Toolbars

1. Overview of Intelligent Makeover Passes

When evaluating an InspectorTemplate, the template engine executes four Intelligent Makeover Passes before or after evaluating individual matching rules:

TEXT
[Template Execution Engine]
         │
         ├───► Pass 1: Relational Companion Pairing
         │     (Pairs min*/max* into HorizontalGroups or MinMaxSliders)
         │
         ├───► Pass 2: Dynamic Companion Binding
         │     (Binds ProgressBar Max values to companion max fields)
         │
         ├───► Pass 3: Progressive Toggle Cascades
         │     (Wires boolean switches to conditionally hide child fields)
         │
         └───► Pass 4: Action Toolbar Synthesis
               (Organizes parameterless methods into interactive button bars)

Each pass can be toggled on or off per template via checkboxes in InspectorTemplate or in the Makeover Wizard.

2. Pass 1: Relational Companion Pairing

  • Setting: EnableRelationalPairing = true
  • Behavior: Scans the target component for companion field pairs based on naming patterns:
    • minDamage and maxDamage
    • startColor and endColor
    • innerRadius and outerRadius
  • Result: Instead of rendering them as separate, disconnected vertical rows, the engine automatically wraps them inside a side-by-side HorizontalGroup("Damage Range") or converts float pairs into a single [MinMaxSlider].

3. Pass 2: Dynamic Companion Binding

  • Setting: EnableDynamicCompanionBinding = true
  • Behavior: Whenever a progress bar attribute is applied to a field (e.g. currentMana), the engine searches for an associated ceiling field (maxMana or totalMana).
  • Result: It automatically sets ProgressBar.MaxMember = "maxMana" instead of a hardcoded constant (100). At runtime, when character stats or player levels increase, the progress bar's maximum range automatically scales with the game's actual data.

4. Pass 3: Progressive Toggle Cascades

  • Setting: EnableToggleCascades = true
  • Behavior: Detects boolean toggle switches that govern feature subsystems (e.g. hasShield, useGravity, enableAudioFX).
  • Result: Automatically injects conditional visibility attributes (like [ConditionalField("hasShield")] or [ShowIf("hasShield")]) onto related child parameters (shieldCapacity, rechargeDelay, shieldColor).
  • Impact: Cluttered inspectors with 50+ fields collapse into clean, progressive interfaces where advanced settings only appear when their master feature toggle is enabled.

5. Pass 4: Action Toolbar Synthesis

  • Setting: EnableActionToolbar = true
  • Behavior: Scans the target component for parameterless public or private methods (e.g. Respawn(), TriggerExplosion(), ResetSensors(), ClearCache()).
  • Result: Automatically adds [Button] attributes to these methods and groups them horizontally using [ButtonGroup("Actions")] at the bottom of the inspector. Developers and testers get 1-click debug actions in both Edit Mode and Play Mode without writing custom editor buttons.

1. Why Bake to Code?

While virtual profiles (InspectorProfile) are ideal for rapid visual iteration without triggering script recompilation, production workflows frequently require inspector styling to be permanent in C# source code:

  1. Source Control Tracking (Git / Perforce / PlasticSCM): Visual diffs of attributes are visible directly in pull requests alongside gameplay changes.
  2. Zero-Dependency Package Exports: Exportable as standalone .unitypackage or UPM packages that can be used by third-party buyers or other teams who do not have MSUltimate-InspectorCustomizer installed.
  3. IDE Code Navigation: Attributes are visible directly in Visual Studio, Rider, and VS Code for code-completion and refactoring.

Code Baking bridges this gap by permanently writing your virtual attribute configurations into your C# script source files using AST-inspired token replacement.

1. Safe AST-Driven Source Injection

Rewriting source code files automatically carries the risk of damaging formatting, corrupting comments, or breaking existing code syntax.

AttributeCodeBaker utilizes an AST-inspired token scanner rather than blind text replacement:

  • Comment Preservation: Doc comments (/// <summary>), inline comments (//), and block comments (/* ... */) are 100% preserved in their exact locations.
  • Indentation & Formatting Awareness: Injected attributes automatically inherit the indentation level (tabs or spaces) of the declaring member.
  • Access Modifier Safety: Attributes are strictly placed immediately above the target member declaration, below any existing preprocessor directives (#if UNITY_EDITOR).

2. Namespace & using Directive Auto-Import

MSUltimate attributes reside across several runtime namespaces:

  • MaharajaStudio.MSUltimate.Runtime (Core attributes)
  • MaharajaStudio.MSUltimate.AnimatedAttributes (Animated attributes)
  • MaharajaStudio.MSUltimate.ComponentDesigner (Class stylers)
  • MaharajaStudio.MSUltimate.Validation (Validation rules)

When baking code:

  1. AttributeCodeBaker inspects the attribute types being injected.
  2. It scans the top of the C# script for existing using directives.
  3. If a required namespace is missing, it automatically inserts the clean using statement at the top of the file without creating duplicates.

  • Atomic File Writing: Modified files are written via temporary buffer streams. If a disk write error occurs, the original script is unaffected.

2. Key Isolation & Storage Architecture

Developers can control how API keys are handled using the Store Key in EditorPrefs setting on each provider:

  1. Local EditorPrefs (StoreKeyInEditorPrefs = true, Default & Recommended):
    • Keys are stored strictly in the local developer machine's operating system preferences via Unity EditorPrefs (MSUltimate_AI_Key_{ProviderType}).
    • The serialized _apiKey string inside the AIProfile asset on disk remains completely empty (string.Empty).
    • Pushing project changes or sharing branches across Git, GitHub, GitLab, or Perforce will never leak corporate or personal API keys.
  2. Serialized in AIProfile Asset (StoreKeyInEditorPrefs = false):
    • The key is saved directly inside the AIProfile.asset file.
    • Intended exclusively for shared internal development environments where team members deliberately share a dedicated studio development API key without configuring it on each machine.

3. Data Transmission Safeguards

  • Zero Implementation Transmission: The AI Decorator strictly never parses or transmits method bodies, physics loops, shaders, private mathematics, or gameplay algorithms. Only variable names, data types, and doc comments are extracted.
  • Granular Member Filters: Inside the Privacy settings tab, developers can toggle exactly which member categories are allowed for extraction (Public Fields, Serialized Private Fields, Action Methods, Existing Attributes, Doc Comments).
  • Wildcard Ignored Patterns: Exclude internal or compiler-generated variables using comma-separated patterns (e.g. m_*, _internal*, *BackingField).
  • Safety Max Members Cap: Enforces a hard limit on total members extracted per component (default: 120), guarding against runaway token consumption on monolithic classes.
  • Transparent JSON Review: The Raw Payload & Schema tab in AIDecoratorModalWindow lets developers review the exact payload and prompt strings before dispatching any network request.

2. Comprehensive Breakdown of All 8 Categories

2.1 Category 1: General

  • Auto-Update Triggers:
    • Inspector Updates: Controls inspector redraw behavior (LiveDebounced for smooth debounce, Immediate for instant redraw on every keystroke, or ManualOnly).
    • Hierarchy Updates: Controls scene hierarchy redraws (OnlyHierarchyAttributes to update only when hierarchy attributes change, Always, or ManualOnly).

    • Debounce Delay (ms): Controls throttle slider delay (50ms to 1000ms, default: 300ms) for smooth parameter dragging without editor stutter.
  • Persistence & Workflow:
    • Auto-Save Profile on Edit: When enabled, any card edit automatically writes to the profile asset on disk.
    • Live In-Memory Preview: Enables instant reflection preview in active inspectors before disk saves.
    • Auto-Explore Code Attributes on Load: When enabled, scans and imports code-defined attributes when selecting a component. If disabled (recommended), import manually via the 🔍 Explore button in the toolbar so cleared attributes are not continuously re-imported.
